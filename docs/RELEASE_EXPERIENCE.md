## 1. 2FA 授权窗口**有时效**：约 5 分钟（小样本实测，2026-10-13 观测）

`RELEASING.md` 第 7 步与 FAQ 都已写明「非 TTY 时链接会被遮蔽并立刻退出」。**但那里没有写：拿到链接之后，
你只有约 5 分钟。**

**机制**（读 npm 自身源码得来，非推测）：

```
npm-profile/lib/index.js 的 webAuthCheckLogin()
  GET /-/v1/done?authId=…  → 202（还没确认）→ 按响应的 `retry-after` 头再等（实测约 3 秒）→ 递归重试
  GET /-/v1/done?authId=…  → 200 + {token}  → 成功，继续 PUT 上传
  GET /-/v1/done?authId=…  → 404             → 该 authId 已作废，非交互/超时都会走到这里
```

`npm publish` 的顺序是 **`PUT`（未授权，得 401）→ web-auth 轮询 → 授权后再 `PUT` 上传**。
所以**轮询期间包一个字节都没上传**：超时是**真失败**，且重试安全（**不需要改版本号**）。

**实测对照**（2026-10-13 观测。**证据来源要说清**：这两次是在**同族的 `dsh-connect-qoder` 发布 0.4.3 时**
记录的 —— workbuddy 自身的历史发布**从未走到超时这条路径**。之所以记在这里，是因为 2FA 与轮询都是
**npm 账号级**（同一个 `dmh2002`）行为，与包无关）：

| 会话 | 轮询次数 | 末次响应 | 结果 |
| --- | --- | --- | --- |
| AI 代跑（把链接转述给人等回复） | 约 **92** 次（≈4.6 分钟）后耗尽 | **`GET 404`** | `PUT 401`、`exit 1`，**真失败** |
| 维护者在**自己的终端**里跑 | **13** 次（约 49 秒） | **`GET 200`** | `PUT 202`、`exit 0`、`+ …@X.Y.Z` |

> **可操作的结论**：**别把授权链接转述给别人、等对方切窗口确认再回复** —— 一次人工往返就吃掉大半窗口。
> 需要 2FA 的发布会话，直接在**自己的交互式终端**里跑 `npm publish`：npm 会自动打开浏览器并**在终端里原地等待**，
> 当场确认即可。
>
> ⚠️ **一条实测的附注**：用 `script -q /dev/null npm publish` 伪造 pty **确实能绕过**「非 TTY 就遮蔽链接」
> 这一层（实测 `process.stdout.isTTY === true`、链接明文可见），**但绕不过时效** —— 上述 AI 代跑的失败就是证据。
> 所以「用 pty 包装一下」不是解法，`RELEASING.md` 里「交回自己的终端」才是。

## 2. `authId` 在日志里也是 `***`：**不能用它做归属**（实测）

`RELEASING.md` 的 FAQ 已记「授权链接被 npm 自己印成 `***`，日志里同样只有 `***`」。**补充一条同源的**：

**轮询 URL 的 `authId` 参数也被 npm 遮蔽**，`~/.npm/_logs/*-debug-0.log` 里同样是 `authId=***`。

**所以不要试图用 authId 回答「这条链接属于哪次运行」** —— 它**不可能**出现在任何日志里。2026-10-13 那次
我就据此下过一个错结论（「在我的日志里搜不到这个 authId，所以不是我的运行」），而那是**必然搜不到**的，
属于无效推理。**要归属，改用这些指纹**：

| 想知道的 | 可用的判据 |
| --- | --- |
| 那次是**成功**还是超时 | 轮询次数与末次响应：十几次就 `GET 200` = 当场确认成功；近百次后 `GET 404` = 超时 |
| 那次**有没有上传** | 日志里有没有 `PUT 202`（只有 `PUT 401` = 没上传） |
| 那次**是谁跑的** | 日志起始时间（文件名即 UTC 时间戳）+ `~/.zsh_history` 里的 `npm publish` |
| 那次**到底成没成** | 回到 `RELEASING.md` 第 8 步的 `curl --noproxy '*'` 直连核验（**永远以它为准**） |

## 3. npm 日志**不是档案**：`logs-max:10` 会静默轮转（实测）

npm 的日志保留上限是 **10 份**（每次新命令的 `debug-0.log` 开头都会记 `logs-max:10 dir:…` 并删掉最旧的一份；
实测同一秒内还会因 `prepack` 另开一份）。**这有一个实际后果**：

> 2026-10-13 排查发布问题时，我想回头核对当天早前几次尝试的**确切时间与轮询次数**，
> **那两份日志已经不存在了** —— 被后续命令轮转删除。所以那份「失败记录表」里有几行只能标注「不可再核」。

**纪律**：发布当天**只跑必要的命令**（每条命令都会挤掉一份日志），并且**尽早把关键证据摘出来**
（`PUT` 状态行、轮询次数、末次响应、退出码）。**唯一能长期回看的是你写下的备忘与 registry 的实际状态** ——
这也正是本文档存在的理由。

## 4. 核验「修复是否进了发布包」：别用源码字面正则 grep 产物（实测）

`RELEASING.md` 第 8 步要求核对 shasum 一致，这解决「发的是不是这份构建」。**但如果你还想确认某个修复
在包里**，注意下面这个坑（2026-10-13 实测，差点误报「修复没进包」；**观测发生在同族 `dsh-connect-qoder`**，
但成因是**构建器行为**——本仓库用的是同一个 `tsdown`，所以同样适用）：

**构建会提升/重命名标识符**，所以拿**源码里的字面正则**去 grep `lib/`：

```
# 源码里是内联的：
message.replace(/\b(?:401|403)\b/gu, '4xx')

# 构建后正则被提成模块级常量，调用点变成：
message.replace(SANITIZE_BARE_STATUS, "4xx")
```

**第一次 grep 源码里的正则字面量 → 0 命中**，若据此下结论就是**误报**。可靠的做法有两条：

```bash
# ① grep 语义片段而不是整段源码（短、不含会被改名/换行的结构）
grep -c 'SANITIZE_BARE_STATUS' node_modules/<pkg>/lib/index.js   # 换成你要找的那个标识符

# ② 最可靠：真装一次并跑它（与 RELEASING.md 第 8 步配套）
cd /tmp && rm -rf verify && mkdir verify && cd verify
npm install dsh-connect-workbuddy@X.Y.Z --no-save --registry https://registry.npmjs.org/
node -e 'import("dsh-connect-workbuddy").then(m => console.log(m.WORKBUDDY_CONNECT_VERSION))'
```

> **本仓库自己的同类形态**：`WORKBUDDY_CONNECT_VERSION` 是**构建期注入**的
> （`tsdown.config.ts` 的 `__DSH_WORKBUDDY_VERSION__`，见 `src/version.ts`）。所以：
> 判据是**运行时导出的那个值**，不是 `grep`；产物里出现旧版本号字面量**不一定**有问题
> （代码注释可能引用历史版本）；而「改完 `package.json` 要重新 build」由 `prepack` 自动兜住。

## 5. 给 AI 助手代跑发布：分工边界（**不可省略**）

`RELEASING.md` 要求发布相关动作需用户明确确认。结合 §1 的时效问题，建议把边界固定为：

| 谁 | 做什么 |
| --- | --- |
| **AI** | 跑 `pnpm run check`、核对溯源/平台/宿主范围、改版本号、写 CHANGELOG、commit、打 tag、`git push`、盯 CI 双平台、**核验发布结果**（第 8 步直连 + shasum 对比）、建 GitHub Release |
| **用户** | `npm login`（若需要）与 **`npm publish`** —— 在**自己的交互式终端**里跑，当场完成浏览器确认 |

**AI 把工作做到「一切就绪、只差在用户终端敲一条 `npm publish` 并点确认」为止**，是最省事的边界。
理由有两条：一，**凭据不该交给 AI**；二，**2FA 窗口只有约 5 分钟**（§1），转述链接的人工往返赶不上。

**同类观察（2026-10-13，实测）**：AI 代跑 4 次全部失败（含用 `script` 伪造 pty），耗费约 20 分钟、
刷出 3 条作废的授权链接；用户在自己终端里跑的那一次，**49 秒**完成，日志形态正是
`PUT 401 → web-auth 轮询 → PUT 202 → "being processed"`。

> **发布状态判别顺序**（与 `RELEASING.md` 第 8 步一致）：**先读 `~/.npm/_logs` 里那次运行的日志，再查 registry**。
> 日志能区分「正在处理」与「根本没发」（`RELEASING.md` 已给出完整三态判据）；registry 只能告诉你「现在还没有」。
> **最终定论永远以第 8 步的 `curl --noproxy '*'` 直连为准**（本机 `~/.npmrc` 配了 7897 代理，会读到缓存旧版本）。

## 6. 尚未做的（如实登记，沿用 `docs/WINDOWS.md` §6 的体例）

- **§1 的时效数字是「单机单包、两个会话」的观测**（小样本实测）：92 次耗尽 / 13 次成功这两组是实测，
  「约 5 分钟」是由 `retry-after` ≈3 秒 × 轮询次数推出。**npm 若改了 `retry-after` 或轮询上限，此数会变。**
- **§1 失败那两次的原始日志已按 §3 被轮转删除**，因此那张对照表**无法从本机日志重新复现**，只有成功那次的
  日志（`2026-10-13T05_57_00_212Z`）与 registry 的 `time` 字段仍在。
- **本文档未在 Windows 上核对过 2FA 流程**（§1~§5 都在 macOS 上观测）。Windows 上 npm 打开浏览器的行为、
  以及 `script` 的替代品（Windows 无 `script -q`）**均未验证**（按本文档口径属**未验证**）；`RELEASING.md` 第 2.5 步
  要求 Windows 是一等目标平台，若今后在 Windows 上发布遇到 2FA 问题，请在此补记。
